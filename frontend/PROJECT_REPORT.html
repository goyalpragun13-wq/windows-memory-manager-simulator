Author: Pragun Goyal GitHub: @goyalpragun13-wq Date: October 2026 Platform: FastAPI & Modern Web

Abstract

Traditional computer science education introduces virtual memory through simplified, monolithic global page replacement algorithms (such as global FIFO or global LRU operating across an undifferentiated physical frame pool). In contrast, commercial operating systems—most notably Microsoft Windows NT, 10, and 11—utilize a sophisticated two-tier paging architecture that decouples per-process Working Sets (WS) from a centralized Page Frame Number (PFN) Database. This report presents the mathematical modeling, full-stack architectural design, and experimental evaluation of an interactive Windows Virtual Memory Manager Simulator. The system models working set trimming, 5-state PFN frame transitions (Active, Standby, Modified, Free, Zeroed), zero-disk-I/O Soft Page Faults, the Modified Page Writer, an idle-priority Zero-Page Thread, hardware MMU address decomposition with a 4-entry associative TLB, and empirical page replacement bounds including automated detection of Belady's Anomaly. Validated with 22 automated pytest verification assertions achieving 100% test passing rate, the simulator serves as a high-fidelity platform for operating systems education and research.

1. Introduction & Problem Statement

Virtual memory provides executing processes with the illusion of a private, continuous address space while multiplexing limited physical RAM across concurrent workloads. While introductory textbooks present paging as a simple global algorithm replacing pages in a uniform array of frames, real operating systems face complex requirements: process working set isolation, protection against inter-process information leakage, mitigation of synchronous disk write penalties, and rapid recovery of recently trimmed pages.

The objective of this project is to model and simulate the internal virtual memory architecture of Microsoft Windows, providing both an extensible Python/FastAPI backend engine and an interactive web dashboard for empirical exploration and laboratory assignments.

2. Theoretical Foundations & Windows Architecture

2.1 Two-Tier Paging & Working Sets

The Windows Virtual Memory Manager (VMM) segregates physical memory into two tiers:

  • Per-Process Working Sets (WS): The set of virtual pages currently mapped in physical RAM for each active process ($P_1, P_2, P_3$). Each process is governed by a working set quota ($WS_{\text{limit}}$).
  • Global Page Frame Number (PFN) Database: A kernel database maintaining the state of all 16 physical frames and managing unmapped or cached pages across specialized system lists.

2.2 The 5-State PFN Database State Machine

Every physical frame in RAM is categorized into one of five states:

  1. Active (Valid): Mapped in a process's working set (Valid bit = 1 in hardware Page Table Entry).
  2. Standby List: Clean pages trimmed from a working set. Still retains the virtual page content and can be reclaimed via an in-memory Soft Fault with zero disk I/O.
  3. Modified List: Dirty pages ($d=1$) trimmed from a working set. Must be written to `pagefile.sys` before the frame can be repurposed.
  4. Free List: Unallocated frames containing uninitialized stale data.
  5. Zeroed List: Frames pre-cleared by the idle-priority Zero-Page Thread, preventing cross-process data leakage.

2.3 Soft Faults vs. Hard Faults Mathematical Latency Model

Let the effective memory access time be defined as:

T_{\text{effective}} = (1 - P_{\text{fault}}) \cdot T_{\text{RAM}} + P_{\text{fault}} \cdot T_{\text{service}}

Under the Windows two-tier architecture, total page faults split into soft faults and hard faults:

T_{\text{service}} = \frac{P_{\text{soft}}}{P_{\text{fault}}} \cdot T_{\text{soft}} + \frac{P_{\text{hard}}}{P_{\text{fault}}} \cdot T_{\text{hard}}

Because $T_{\text{soft}} \approx 200\,\text{ns}$ (in-memory list unlinking) while $T_{\text{hard}} \approx 10,000,000\,\text{ns}$ (disk/pagefile I/O), soft faults execute approximately 50,000 times faster than hard page faults.

3. System Design & Software Engineering

The simulator is engineered with strict separation of concerns:

  • Core Kernel Engine (Python 3.13): Implemented in backend/app/core/ with object-oriented modules for PfnDatabase, WorkingSetManager, MMU, TLB, and WindowsMemoryManager.
  • REST API Layer: Built using FastAPI, featuring asynchronous request handling, Pydantic v2 data validation schemas, and auto-generated Swagger documentation at /docs.
  • Modern Responsive Frontend: Built with HTML5/CSS3/ES6 featuring dark/light themes, a 16-frame dynamic physical memory grid, interactive MMU address translator, algorithm lab, and a guided 8-step pedagogical tour.
  • Continuous Integration & Docker: GitHub Actions workflow executing pytest across Python 3.11, 3.12, and 3.13; multi-stage Docker containerization for one-click deployment.

4.3 Empirical Demonstration of Belady's Anomaly

The replacement algorithm lab tested the Belady Reference String $\sigma = \langle 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 \rangle$:

Algorithm 1 Frame 2 Frames 3 Frames 4 Frames 5 Frames 6+ Frames
FIFO 12 12 9 10 ⚠️ (Anomaly) 5 5
LRU 12 12 10 8 5 5
Clock 12 12 10 10 5 5
OPT (Belady MIN) 12 12 7 6 5 5

As mathematically established by L. A. Bélády (1966), FIFO faults increased from 9 to 10 when frames expanded from 3 to 4, whereas stack algorithms (LRU) and the theoretical optimum (OPT) demonstrated monotonic non-increasing fault profiles.

5. Automated Test Suite & Invariant Proofs

The project contains 22 automated pytest tests validating the following invariants:

  1. Physical Frame Conservation: $\sum |WS_p| + |L_{\text{free}}| + |L_{\text{zero}}| + |L_{\text{stby}}| + |L_{\text{mod}}| \equiv 16$ holds at every discrete clock cycle.
  2. TLB Residency Invariant: No TLB entry ever points to an unmapped, invalidated, or evicted page.
  3. OPT Minimality Theorem: $OPT(\sigma, f) \le \min(FIFO(\sigma, f), LRU(\sigma, f), Clock(\sigma, f))$ holds across all workloads and frame capacities.

Pytest Execution Summary: 22 passed, 0 failed in 1.26s (100% success rate).

The Windows Memory Manager Simulator provides a comprehensive, academically sound implementation of a production virtual memory subsystem.
